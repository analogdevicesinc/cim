Core Concepts
=============

This page explains the fundamental ideas behind CIM and how they fit together.

Workspace
---------

A **workspace** is a self-contained directory that holds everything needed for
a project: cloned git repositories, toolchains, downloaded files, Python
virtual environment, generated Makefile, and configuration files.

A workspace is identified by a ``.workspace`` marker file at its root. It
typically contains:

.. code-block:: text

   ~/dsdk-my-project/
   ├── .workspace              # marker file
   ├── sdk.yml                 # manifest (copied from the target)
   ├── os-dependencies.yml     # OS deps (if the target defines them)
   ├── python-dependencies.yml # Python deps (if the target defines them)
   ├── Makefile                # generated by cim makefile / cim init --install
   ├── .venv/                  # Python virtual environment
   ├── .cim/                   # install sentinels, per-repo venvs, overlays
   ├── toolchains/             # extracted toolchains (paths set by the manifest)
   ├── repo-a/                 # cloned git repos
   └── repo-b/

Workspaces are isolated — everything lives in the workspace folder except host
OS packages and the shared mirror. Deleting the workspace directory removes
everything cleanly.

Mirror
------

The **mirror** is a machine-local cache (default: ``$HOME/tmp/mirror``) that
stores:

- Git bare repository mirrors (used for faster subsequent clones)
- Downloaded toolchain archives
- Cached ``copy_files`` artifacts

The mirror is shared across workspaces. When you initialize a second workspace
that uses the same repository, CIM clones from the local mirror instead of
fetching from the network again. This saves bandwidth and enables offline
operation.

The mirror is not part of any manifest. Its location is resolved in this order
(highest first): the ``--mirror`` flag, ``mirror`` under ``[workspace]`` in
the configuration file, then the built-in default. Disable mirroring
per-command with ``--no-mirror`` or globally with ``no_mirror = true`` under
``[workspace]`` (see :doc:`/reference/configuration`).

.. note::

   Workspaces initialized from a mirror borrow git objects from it via git
   alternates (``.git/objects/info/alternates``). Your working tree and local
   commits are always safe, but git operations that walk history
   (``git log``, ``git checkout <old-sha>``) fail if the mirror is removed.
   Running ``cim update`` restores the mirror. To make a repository fully
   independent of the mirror, run ``git repack -a -d`` inside it and then
   delete ``.git/objects/info/alternates``.

Target
------

A **target** is a predefined project configuration inside a manifest
repository. Each target is a directory under ``targets/`` containing at
minimum an ``sdk.yml`` file.

.. code-block:: text

   my-manifests/
   └── targets/
       ├── optee-qemu-v8/
       │   ├── sdk.yml
       │   ├── os-dependencies.yml
       │   └── python-dependencies.yml
       └── adi-linux/
           └── sdk.yml

Targets are what users select with ``cim init --target <name>``.

Manifest Repository
-------------------

A **manifest repository** is a git repository (or local directory) that
contains one or more targets.

Organizations typically maintain:

- An **internal** manifest repository with all their projects
- An **external** manifest repository for customers and partners

CIM discovers targets by scanning the ``targets/`` directory of the manifest
repository. Point CIM at a manifest repository with ``--source``, or set
``default_source`` in the configuration file.

Manifest
--------

The **manifest** is the set of YAML files that describe a target. The primary
file is ``sdk.yml``, which defines:

- Git repositories to clone
- Build, test, clean, and flash commands
- Toolchains to download
- Files to copy
- Variables for overridable settings
- Custom install targets

Two optional companion files define host dependencies:

- ``os-dependencies.yml`` — system packages per OS and distribution
- ``python-dependencies.yml`` — Python packages organized into profiles

See :doc:`/reference/manifest` for the complete field reference.

How It All Fits Together
------------------------

.. mermaid::

   sequenceDiagram
     autonumber
     actor U as User
     participant C as cim
     participant R as Manifest repository
     participant M as Mirror
     participant W as Workspace

     U->>C: cim list-targets --source URL
     C->>R: scan targets/
     C-->>U: available targets and versions
     U->>C: cim init --target my-project --install
     C->>R: fetch sdk.yml and dependency files
     C->>M: update git mirrors, download toolchains and files
     C->>W: clone repos from the mirror, copy manifest files
     C->>W: extract toolchains, create .venv, install Python packages
     C->>W: generate Makefile, run install steps
     U->>W: make sdk-build / make sdk-test

The workflow in detail:

1. ``cim list-targets --source <repo>`` discovers available targets.
2. ``cim init --target my-project`` clones repos (via the mirror), copies the
   manifest files, and sets up the workspace.
3. Dependencies are installed. ``cim init --install`` does this in the same
   step: it installs toolchains and Python packages, generates the Makefile,
   and runs the manifest's install steps. ``--full`` also installs OS
   packages. Without either flag, run ``cim install os-deps``,
   ``cim install toolchains``, ``cim install pip``, ``cim makefile``, and
   ``cim install tools --all`` yourself.
4. ``make sdk-build`` / ``make sdk-test`` runs the build.
